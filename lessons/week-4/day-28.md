## 개념 설명

### 왜 계획을 먼저 쓰는가

지난 며칠 동안 선택을 많이 했습니다. 어떤 과제를 쓸지, 어느 손목을 쓸지, 처음 몇 초를 버릴지, 어떤 feature를 볼지, 누구를 제외할지. 각 선택마다 두세 가지 길이 있었다면, 조합은 수십에서 수백 가지입니다. 이 가운데 **결과가 가장 좋게 나오는 조합**을 고르는 것은 아주 쉽고, 아주 위험합니다. 진짜 차이가 없어도 수백 번 시도하면 몇 번은 우연히 "유의"하게 나옵니다. 이것이 **p-hacking**입니다.

임상시험이 시작 전에 주 평가변수(primary endpoint)를 등록하는 것과 같은 이유입니다. 시험이 끝난 뒤에 "혈압은 안 내렸지만 콜레스테롤은 내렸다"고 평가변수를 바꾸면 믿을 수 없습니다. 분석 계획서는 **미래의 나를 묶어 두는 약속**입니다. 연구를 시작하기 전에 계획을 공개적으로 적어 두는 것을 preregistration(사전등록)이라고 하는데, 오늘 쓰는 문서는 그 개인용 축소판입니다.

계획대로 하지 않으면 안 된다는 뜻은 아닙니다. 계획에 없던 분석도 할 수 있습니다. 다만 그것을 **탐색적(exploratory)** 이라고 표시해서, 미리 정한 **확증적(confirmatory)** 분석과 구분합니다. 이미 어제 그림을 그려 봤으니 완전히 "결과를 모르는" 상태는 아닙니다. 그 사실도 계획서에 정직하게 적습니다.

### 계획서의 다섯 칸

**① 주요 outcome 1–2개.** 군을 비교할 feature를 하나, 많아야 둘만 고릅니다. 과제, 손목(또는 발), 요약 방법까지 포함해 **한 문장으로 계산 가능하게** 적습니다. 나머지 feature는 "2차 또는 탐색적"으로 분류합니다. outcome을 줄이는 것은 2주차에 배운 다중검정 부담을 줄이는 가장 확실한 방법입니다.

**② 군 비교 방법.** 어느 군과 어느 군을 비교하는지(예: PD 대 건강 대조군. 다른 진단군은 어떻게 할지), 분석 단위(참가자 1명 = 1 관찰), 무엇을 보고할지(효과크기와 신뢰구간, 그리고 검정 방법)를 적습니다. 구체적인 검정 선택은 5주차 Day 29–30에서 다루니, 오늘은 "참가자 단위 요약값을 군 간 비교, 효과크기와 95% 신뢰구간을 함께 제시"까지 적으면 됩니다.

**③ 제외 기준.** Day 25의 flowchart 기준을 옮기고, 기록 수준의 기준(예: 결측 비율, 기록 길이)과 참가자 수준의 기준을 구분합니다. 모두 **결과와 무관한** 품질 기준이어야 합니다.

**④ 검증 방식.** 5주차에 분류 모델을 만든다면, 데이터를 어떻게 나눌지 미리 정합니다. 핵심은 한 줄입니다. **참가자 단위로 나눈다.**

**⑤ 한계.** 이 데이터와 설계가 답할 수 없는 것을 적습니다. 단면 연구라서 진행을 볼 수 없다, 한 기관의 자료다, 군 간 나이·성별 분포가 다르다, 약 복용 상태를 모른다(확인한 범위에서), 진단이나 인과를 말할 수 없다, 3주차 마우스 결과와 직접 연결할 수 없다 등입니다.

### 4주차 핵심 규칙을 계획에 넣기

이번 주 내내 반복한 세 가지 규칙을 계획서의 문장으로 바꿉니다.

**규칙 1 — 반복 측정은 서로 독립적인 표본이 아닐 수 있다.** 계획서에는 "분석 단위는 참가자이다. 한 참가자의 여러 기록(과제, 손목, 반복, window)은 참가자당 하나의 값으로 요약한 뒤 비교한다"라고 적습니다. 이것을 어기면 어떻게 되는지는 예시 1에서 숫자로 봅니다. 차이가 전혀 없는데도 "유의하다"는 결과가 절반 넘게 나옵니다.

**규칙 2 — 시계열을 무작위로 자른 뒤 train/test에 섞는 방식은 사용하지 않는다.** 한 사람의 신호를 window로 자르면 이웃한 조각끼리는 거의 같은 모양입니다. 이 조각들이 train과 test에 나뉘어 들어가면, 모델은 질병의 특징이 아니라 **그 사람의 특징**을 외워 test를 맞힙니다. 시험 문제를 미리 본 것과 같아서 이것을 **데이터 누수(data leakage)** 라고 합니다. 계획서에는 "한 참가자의 모든 기록은 train 또는 test 중 한쪽에만 속한다"라고 적습니다.

**규칙 3 — feature를 계산하기 전 단위, 시간축, 결측값, artifact를 점검한다.** 계획서에는 점검 절차를 구체적 숫자로 적습니다. 예: "sampling rate 100 Hz 확인, 처음 0.5초 제거, 결측이 있는 기록은 제외".

### 쓸 수 있는 문장과 쓸 수 없는 문장

마지막으로 표현의 경계를 정합니다. 이 프로젝트의 결과로 쓸 수 있는 문장은 "이 데이터셋에서 PD군의 [feature]가 대조군보다 [효과크기]만큼 컸다(95% CI …)" 정도입니다. 쓸 수 없는 문장은 "이 feature로 PD를 진단할 수 있다", "떨림이 클수록 병이 심하다"(중증도 자료로 확인하지 않았다면), "스마트워치로 조기 진단이 가능하다" 같은 것입니다. 표본이 작으면 결과는 가설 생성 수준이고, 한 데이터셋 안에서의 검증은 외부 검증이 아닙니다. 계획서의 "한계" 칸에 이 금지 문장들을 미리 적어 두면, 5주차 보고서를 쓸 때 스스로를 점검하는 기준이 됩니다.

## 예시로 이해하기

### 예시 1: 반복 측정을 독립으로 세면 생기는 일

두 군 사이에 **진짜 차이가 없는** 가상 세계를 2,000번 만들어, 두 가지 방법으로 검정합니다. 차이가 없으니 "유의하다(p < 0.05)"고 나오는 비율은 5% 근처여야 정상입니다.

```python
import numpy as np
from scipy import stats

rng = np.random.default_rng(0)
n_sim, n_person, n_rec = 2000, 10, 20     # 군당 10명, 한 사람당 기록 20개
false_pos_records = 0
false_pos_persons = 0

for _ in range(n_sim):
    # 두 군 사이에 진짜 차이는 '없다'. 사람마다 고유한 수준(person effect)만 다르다.
    def make_group():
        person_level = rng.normal(0, 1.0, n_person)                              # 사람 간 차이
        return person_level[:, None] + rng.normal(0, 0.5, (n_person, n_rec))     # 사람 내 흔들림
    a, b = make_group(), make_group()

    # 잘못된 방법: 기록 200개씩을 독립 표본처럼 비교
    if stats.ttest_ind(a.ravel(), b.ravel()).pvalue < 0.05:
        false_pos_records += 1
    # 올바른 방법: 사람별 평균 10개씩을 비교
    if stats.ttest_ind(a.mean(axis=1), b.mean(axis=1)).pvalue < 0.05:
        false_pos_persons += 1

print(f"기록 단위 비교의 거짓 양성 비율: {false_pos_records / n_sim:.1%}")
print(f"참가자 단위 비교의 거짓 양성 비율: {false_pos_persons / n_sim:.1%}")
```

출력 (실행 확인):

```text
기록 단위 비교의 거짓 양성 비율: 64.6%
참가자 단위 비교의 거짓 양성 비율: 5.0%
```

기록을 독립 표본처럼 세면, 차이가 없는데도 **약 65%** 의 확률로 "유의한 차이"를 보고하게 됩니다. 사람별 평균으로 접으면 기대대로 5%입니다. 표본이 200개로 보이지만 실제 정보는 10명분뿐이기 때문입니다.

### 예시 2: 줄 단위 split과 참가자 단위 split

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(0)
ids = np.repeat([f"S{i:02d}" for i in range(1, 11)], 6)      # 10명 × 기록 6개 = 60줄
df = pd.DataFrame({"participant_id": ids, "window": np.tile(np.arange(6), 10)})

# 잘못된 방법: 줄(window)을 무작위로 섞어 80/20
shuffled = df.sample(frac=1, random_state=0)
train_bad, test_bad = shuffled.iloc[:48], shuffled.iloc[48:]
overlap_bad = set(train_bad["participant_id"]) & set(test_bad["participant_id"])

# 올바른 방법: '사람'을 섞어 8명/2명으로 나눈 뒤, 그 사람의 줄을 통째로 보낸다
people = rng.permutation(df["participant_id"].unique())
test_people = set(people[:2])
train_ok = df[~df["participant_id"].isin(test_people)]
test_ok = df[df["participant_id"].isin(test_people)]
overlap_ok = set(train_ok["participant_id"]) & set(test_ok["participant_id"])

print("줄 단위 split → train·test 양쪽에 다 있는 사람 수:", len(overlap_bad))
print("참가자 단위 split → 양쪽에 다 있는 사람 수:", len(overlap_ok))
print("참가자 단위 split 크기: train", len(train_ok), "줄 / test", len(test_ok), "줄")
```

출력 (실행 확인):

```text
줄 단위 split → train·test 양쪽에 다 있는 사람 수: 7
참가자 단위 split → 양쪽에 다 있는 사람 수: 0
참가자 단위 split 크기: train 48 줄 / test 12 줄
```

줄을 섞으면 10명 중 7명이 train과 test 양쪽에 걸칩니다. 모델은 test에서 "이미 본 사람"을 다시 만납니다. 참가자 단위로 나누면 겹침이 0입니다. 5주차 Day 33에서는 이것을 자동으로 해 주는 `GroupKFold`를 씁니다. 지금 기억할 것은 **"겹치는 사람 수 = 0"을 코드로 확인하는 습관**입니다.

4. **4번 칸**에서 Day 25의 QC 표를 다시 열어 군별 사람 수를 옮겨 적습니다. 가장 작은 군이 몇 명인지 확인하고, 그 수로 무엇을 말할 수 있을지(가설 생성 수준인지) 한 문장을 덧붙입니다.
5. **5번 칸**은 Day 25의 flowchart와 문장이 일치해야 합니다. 다르면 flowchart를 고칩니다.
6. **6번 칸**을 쓴 뒤, 예시 2의 "겹치는 사람 수" 확인 코드를 내 feature table의 참가자 ID 열로 바꿔 한 번 실행해 봅니다.
7. **8번 칸**에 한계를 최소 5개 적습니다. Day 24의 "아직 확인하지 못한 것" 목록에서 해결되지 않은 항목도 여기에 옮깁니다.
8. 파일을 commit합니다. 커밋 메시지 예: `Add PD analysis plan before group comparison`. 이 커밋 시각이 "결과를 보기 전에 계획을 세웠다"는 기록이 됩니다. `learning-log.md`에 4주차 회고를 세 줄로 적습니다.

⚠️ **흔한 오류 1:** outcome을 다섯 개, 열 개씩 적는 것. "혹시 모르니 다 넣자"는 마음이 p-hacking의 시작입니다. 주요 outcome은 1–2개로 제한하고 나머지는 탐색적이라고 표시하세요.

⚠️ **흔한 오류 2:** 제외 기준에 "이상한 값은 제외"처럼 모호하게 쓰는 것. 무엇이 이상한지 숫자로 정해야 합니다(예: "기록 길이가 기대의 90% 미만"). 숫자로 못 정하겠으면 제외하지 말고 민감도 분석 항목으로 옮깁니다.

## 🤖 AI와 함께 하기 (주간 실습, 20–30분)

**이번 주의 기술: 신호처리 코드 작성을 AI에게 도움받고, 단위와 sampling rate를 직접 확인하기**

신호처리 코드는 AI가 빨리 써 주는 분야입니다. 하지만 AI는 여러분 데이터의 **단위**(초인지 밀리초인지, N인지 kg인지)와 **sampling rate**(초당 몇 번 측정했는지, Hz)를 모릅니다. 그래서 흔히 "100 Hz라고 가정하면…"처럼 숫자를 슬쩍 지어 넣습니다. 이 숫자가 틀리면 필터의 차단 주파수, 보폭 시간, 걸음 수가 모두 틀어지는데 코드는 아무 오류 없이 돌아갑니다. 현미경 배율을 잘못 적으면 세포 크기가 전부 틀리는 것과 같습니다.

1. **사실을 먼저 적습니다.** AI에게 묻기 전에, 내 데이터 사전(Day 24)과 데이터셋 페이지에서 확인한 sampling rate, 각 열의 단위, 기록 길이를 적습니다. 확인하지 못한 값은 "[확인 필요]"로 둡니다.
2. **아래 프롬프트로 코드 작성을 요청합니다.** 단위와 sampling rate를 가정하지 말라고 명시합니다.

   ```text
   나는 6주 퇴행성 뇌질환 바이오인포매틱스 실습을 진행 중이다.
   지금은 PhysioNet Parkinson's disease gait 데이터(인간 파킨슨병 보행 데이터) 프로젝트의 4주차다.

   중요한 해석 원칙:
   - PhysioNet 반복 측정/시계열은 참가자 단위로 train/test를 분리해 데이터 누수를 막는다.
   - 결과는 진단이나 치료 권고로 표현하지 않는다.

   오늘의 작업: Day 28 — 분석 계획의 주요 outcome을 계산할 신호처리 코드 초안
   내가 원하는 도움: 코드 디버깅

   데이터 구조(가상 예시, 실제 값 아님):
   - 열 이름: [예: time, left_force, right_force]
   - 단위: [데이터 사전에서 확인한 단위 또는 "확인 필요"]
   - sampling rate: [확인한 값 또는 "확인 필요"]

   요청: 한 기록에서 [outcome, 예: 평균 stride time]을 계산하는 Python 함수

   다음 순서로 답해 달라:
   1. 이 계산의 목적을 한 문장으로 요약
   2. 코드가 가정하는 단위와 sampling rate를 모두 나열(내가 주지 않은 값은 "가정"이라고 표시)
   3. 실행 가능한 단계별 계획
   4. Python 코드(sampling rate는 함수 인자로 받고, 코드 안에 숫자로 박지 말 것)
   5. 결과를 해석할 때 피해야 할 과장 표현
   ```

3. **AI 코드를 돌리기 전에 sampling rate를 데이터에서 역산해 봅니다.** 시간 열이 있다면 간격의 역수가 sampling rate입니다. 아래는 가상 기록으로 확인하는 예입니다.

   ```python
   import numpy as np

   # 가상 기록: 100 Hz로 3초 동안 잰 시간 열(초 단위)과 힘 신호
   t = np.arange(0, 3, 0.01)
   force = 400 + 50*np.sin(2*np.pi*1.0*t)   # 1 Hz로 오르내리는 가상 신호

   fs = 1 / np.median(np.diff(t))           # 시간 간격에서 sampling rate 역산
   print(f"추정 sampling rate: {fs:.1f} Hz")
   print(f"샘플 수 {len(t)}개 / fs = {len(t)/fs:.2f}초 (기록 길이와 맞는지 확인)")
   print(f"시간 열의 마지막 값: {t[-1]:.2f}초")
   ```

   출력:

   ```text
   추정 sampling rate: 100.0 Hz
   샘플 수 300개 / fs = 3.00초 (기록 길이와 맞는지 확인)
   시간 열의 마지막 값: 2.99초
   ```

   내 데이터에서 역산한 값이 데이터셋 페이지의 값과 다르면, 시간 열의 단위(초/밀리초)부터 의심합니다.

4. **결과의 단위를 상식으로 점검합니다.** AI 코드로 계산한 outcome이 생리적으로 말이 되는 범위인지 봅니다. 예를 들어 사람의 stride time이 0.01초나 100초로 나오면 sampling rate나 단위가 어긋난 것입니다. 무엇을 기준으로 판단했는지 계획서에 한 줄 적습니다.

**검증 체크**
- [ ] AI 코드에 박혀 있던 숫자(sampling rate, 차단 주파수, 단위 변환 계수)를 모두 찾아 출처를 확인했다.
- [ ] 데이터에서 역산한 sampling rate가 데이터셋 페이지의 값과 일치한다(다르면 이유를 적었다).
- [ ] 계산된 outcome의 단위를 적었고, 값이 생리적으로 가능한 범위인지 확인했다.

> 🔒 **개인정보·데이터 라이선스 주의:** 참가자 원자료(기록 파일, 행 단위 신호)는 외부 AI에 올리지 않습니다. 열 이름·단위·sampling rate 같은 **구조 정보**와, 위 코드처럼 직접 만든 **가상 신호**만 붙여 넣습니다. PADS는 CC BY-NC-SA 등 라이선스 조건이 있고, 다른 PhysioNet 데이터도 데이터셋 페이지마다 조건이 다르므로 먼저 확인합니다. 이 실습은 학습용이며 진단·치료 판단에 쓰지 않습니다.
> PhysioNet의 자격 심사형 데이터(예: MIMIC 전체판)는 이용 계약상 온라인 AI 서비스에 넣으면 안 됩니다(PhysioNet 2023년 공지: <https://physionet.org/news/post/gpt-responsible-use>, 자세한 내용은 [심화 E — Day E2](../advanced/E-ehr/day-E2.md)).

## 퀴즈

**1.** 참가자 10명씩 두 군, 한 사람당 기록 20개가 있습니다. 군 차이가 실제로 없을 때, 기록 200개씩을 독립 표본처럼 t-test하면 어떤 일이 생깁니까?
(a) 거짓 양성이 5% 근처로 유지된다 (b) 거짓 양성이 5%보다 훨씬 많아진다 (c) 검정력이 떨어진다 (d) 아무 문제 없다

<details><summary>정답 보기</summary>

**(b)**. 오늘 시뮬레이션에서는 약 65%가 나왔습니다. 반복 측정은 서로 독립적인 표본이 아니므로, 기록 수를 n으로 쓰면 불확실성이 과소평가됩니다. 사람별로 요약한 뒤 비교하면 5% 근처로 돌아옵니다.

</details>

**2.** 다음 중 사용하지 말아야 할 검증 방식은?
(a) 참가자를 무작위로 train/test 그룹에 배정 (b) 각 참가자의 신호를 window로 자른 뒤, window를 무작위로 train/test에 배정 (c) 참가자 단위 교차검증 (d) 한 참가자의 모든 기록을 test에만 두기

<details><summary>정답 보기</summary>

**(b)**. 시계열을 무작위로 자른 뒤 train/test에 섞으면 같은 사람의 거의 같은 조각이 양쪽에 들어가 데이터 누수가 생깁니다. 모델이 사람을 외워 성능이 부풀려지고, 새로운 사람에게는 그 성능이 나오지 않습니다.

</details>

**3.** (단답) feature를 계산하기 전에 점검해야 하는 네 가지는 무엇입니까?

<details><summary>정답 보기</summary>

**단위, 시간축, 결측값, artifact**. 분석 계획서의 전처리 칸에 각각을 구체적 숫자(예: 100 Hz, 처음 0.5초 제거)로 적어 두면, 나중에 같은 절차를 그대로 재현할 수 있습니다.

</details>

**4.** 분석 계획을 결과를 보기 전에 쓰는 가장 중요한 이유는?
(a) 보고서 분량을 늘리려고 (b) 여러 선택지 중 결과가 좋은 것만 고르는 일을 막으려고 (c) 코드가 빨라져서 (d) 라이선스 조건이라서

<details><summary>정답 보기</summary>

**(b)**. 과제·손목·feature·제외 기준의 조합이 많아서, 결과를 보고 고르면 우연한 차이를 쉽게 "발견"하게 됩니다(p-hacking). 미리 정한 분석은 확증적, 나중에 추가한 분석은 탐색적으로 구분해 보고합니다.

</details>

**5.** 다음 중 이 프로젝트의 결과로 쓸 수 있는 문장은?
(a) "이 feature로 파킨슨병을 진단할 수 있다." (b) "이 데이터셋에서 PD군의 해당 feature는 대조군보다 컸다(효과크기와 95% CI 제시)." (c) "마우스 뇌의 염증이 이 떨림의 원인이다." (d) "스마트워치로 조기 치료 효과를 볼 수 있다."

<details><summary>정답 보기</summary>

**(b)**. 관찰한 데이터셋 안에서의 군 간 차이를 효과크기와 불확실성과 함께 기술하는 문장입니다. (a)와 (d)는 진단·치료 주장, (c)는 종이 다른 데이터를 인과로 연결한 것이어서 이 과정의 데이터로는 뒷받침할 수 없습니다.

</details>
