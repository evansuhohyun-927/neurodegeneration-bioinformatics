## 개념 설명

### 보고서는 결과 모음이 아니라 하나의 질문에 대한 답이다

3주 동안 만든 것은 많습니다. 정상 보행 이론, 신호처리, FI 계산, LOSO 모델, 실시간 상태기계. 보고서는 그 전부를 담는 곳이 아니라 **하나의 질문**에 답하는 곳입니다. 예를 들어 "Daphnet의 실험실 기록에서, 발목·허벅지·엉덩이 가속도의 window feature는 처음 보는 참가자의 FOG를 얼마나, 얼마나 빨리, 얼마나 많은 오경보와 함께 잡는가?" 같은 질문입니다. 이 질문에는 이미 데이터(Daphnet), 검증 단위(처음 보는 참가자 = LOSO), 지표 세 가지(검출, 지연, 오경보)가 들어 있습니다. [Day 35](../../week-5/day-35.md)의 원칙처럼 보고서는 실험 노트가 아니라 읽는 사람을 위한 안내문입니다.

### 숫자 하나에 붙어야 하는 세 가지: 단위, 분모, 불확실성

FOG 탐지 결과 문장은 쉽게 부풀려집니다. "민감도 80%"라는 숫자 하나에는 최소한 세 정보가 붙어야 합니다. **단위**(0.5초 window인가, 삽화인가), **분모**(참가자별로 계산해 평균했는가, window를 한데 모았는가, 몇 명인가), **불확실성**(참가자가 8명뿐이면 평균이 얼마나 흔들리는가). 참가자 단위 부트스트랩은 window가 아니라 **사람을 다시 뽑아** 평균의 흔들림을 봅니다. window를 다시 뽑으면 같은 사람의 비슷한 window가 독립 표본처럼 취급되어 구간이 가짜로 좁아집니다([Day 33](../../week-5/day-33.md)의 누수와 같은 뿌리).

### 한계는 구체적으로, 다음 단계는 실험으로

한계 절에 "표본이 작다" 한 줄만 쓰면 아무것도 말하지 않은 것입니다. 이 프로젝트의 한계는 구체적으로 쓸 수 있습니다. 실험실 기록이고 과제가 FOG를 많이 유발하도록 설계됐습니다. 참가자가 10명(FOG 8명)이고 한 기관에서 기록했습니다. 라벨은 영상 사후 주석이라 경계에 수백 ms 오차가 있을 수 있고, 삽화의 약 40%가 4초 window보다 짧습니다. 약물 상태와 FOG 유형(떨림/무동)별 성능을 나눠 보지 않았습니다. 일상 환경에서는 라벨 자체가 없어 Salomon 2024도 일상 분석을 탐색적 결과로만 제시했습니다.

"다음 단계"는 Day I20에서 본 근거 사다리 위에 놓습니다. 실험실 window 성능(오늘) → 보정·평가 구간을 분리한 환자별 threshold 시험 → 실시간 장치에서 지연과 오경보를 잰 시험 → cue를 켠 조건과 끈 조건을 객관적 지표로 비교하는 시험 → 일상 환경 검증. 웨어러블 로봇 제어로 이어 가려면, FOG 검출기의 오경보가 로봇의 보조 타이밍 오류가 될 수 있다는 점([R] 14장, 23장)과 주기 가정 제어기가 FOG에서 무너진다는 점(Day I20 직접 해보기 5)을 함께 적습니다.

## 예시로 이해하기

### 예시 1 — 보고서용 참가자별 표와 참가자 부트스트랩 구간

Day I19 예시 2가 저장한 `results/advanced/I/I19_loso_pred.csv.gz`를 읽습니다. 추가 패키지 없이 Markdown 표를 직접 만듭니다.

```python
import numpy as np
import pandas as pd

win = pd.read_csv("results/advanced/I/I19_loso_pred.csv.gz")      # Day I19 예시 2의 출력
rng = np.random.default_rng(21)
rows = []
for s, g in win.groupby("subject"):
    y = g["fog"].to_numpy().astype(bool)
    pred = g["p_RF"].to_numpy() >= 0.5
    rows.append({"참가자": s, "FOG window": int(y.sum()),
                 "민감도(%)": 100 * pred[y].mean() if y.any() else np.nan,
                 "특이도(%)": 100 * (~pred[~y]).mean()})
tab = pd.DataFrame(rows)

def boot_ci(values, n_boot=5000):
    """참가자를 복원추출해 평균의 95% 구간을 구한다(window가 아니라 사람을 다시 뽑는다)."""
    v = np.asarray(values)
    means = [rng.choice(v, len(v), replace=True).mean() for _ in range(n_boot)]
    return np.percentile(means, [2.5, 97.5])

sens = tab["민감도(%)"].dropna(); spec = tab["특이도(%)"]
lo, hi = boot_ci(sens); lo2, hi2 = boot_ci(spec)
# 보고서에 붙일 Markdown 표(추가 패키지 없이 직접 만든다)
md = ["| " + " | ".join(tab.columns) + " |", "|" + "---|" * len(tab.columns)]
md += ["| " + " | ".join("-" if pd.isna(v) else (f"{v:.1f}" if isinstance(v, float) else str(v)) for v in r) + " |"
       for r in tab.itertuples(index=False)]
print("\n".join(md))
print(f"\n민감도: 참가자 평균 {sens.mean():.1f}% (참가자 부트스트랩 95% 구간 {lo:.1f}–{hi:.1f}, n = {len(sens)})")
print(f"특이도: 참가자 평균 {spec.mean():.1f}% (참가자 부트스트랩 95% 구간 {lo2:.1f}–{hi2:.1f}, n = {len(spec)})")
pooled = win["fog"].astype(bool); p = win["p_RF"] >= 0.5
print(f"참고 — window를 한데 모은 민감도 {100 * p[pooled].mean():.1f}%: 사람이 아니라 window를 세면 FOG가 많은 사람이 결과를 좌우한다")
```

실행 결과(Daphnet UCI #245, 2013 기증본, PD 10명 실험실 기록, random forest, LOSO):

```text
| 참가자 | FOG window | 민감도(%) | 특이도(%) |
|---|---|---|---|
| S01 | 206 | 94.2 | 81.2 |
| S02 | 360 | 78.9 | 93.4 |
| S03 | 576 | 94.3 | 80.5 |
| S04 | 0 | - | 96.4 |
| S05 | 947 | 71.9 | 89.6 |
| S06 | 263 | 68.1 | 93.5 |
| S07 | 164 | 81.1 | 89.8 |
| S08 | 403 | 74.9 | 67.7 |
| S09 | 541 | 73.6 | 94.4 |
| S10 | 0 | - | 97.8 |

민감도: 참가자 평균 79.6% (참가자 부트스트랩 95% 구간 73.6–86.3, n = 8)
특이도: 참가자 평균 88.4% (참가자 부트스트랩 95% 구간 82.6–93.3, n = 10)
참고 — window를 한데 모은 민감도 78.4%: 사람이 아니라 window를 세면 FOG가 많은 사람이 결과를 좌우한다
```

8명뿐이라 구간이 넓습니다. 그리고 이 구간은 "이 10명이 대표하는 집단"에 대한 것이지, 실험실 밖이나 다른 장비·과제로 넓혀 주는 것이 아닙니다. 부트스트랩은 참가자 수가 이렇게 작을 때 구간을 정확히 주지 못하므로, 보고서에는 참가자별 표 자체를 함께 싣습니다.

### 예시 2 — 결과 문장: 과장 → 절제

| 과장된 문장 | 무엇이 문제인가 | 고친 문장 |
|---|---|---|
| 우리 모델은 FOG를 80% 정확도로 진단한다. | "진단"은 임상 주장, "정확도"는 단위 없음 | Daphnet 실험실 기록 10명에 대한 LOSO에서, RF의 0.5초 window 민감도는 FOG가 있는 8명 평균 79.6%(참가자별 68.1–94.3%)였다. |
| FOG 삽화의 92%를 놓치지 않고 실시간으로 잡았다. | 실시간 장치에서 잰 것이 아님, 허용 규칙 누락 | 삽화가 끝난 뒤 2초까지의 경보를 검출로 인정하면, 237개 삽화 중 92.0%에서 경보가 켜졌다(오프라인 모의 평가). |
| 경보가 FOG 시작 전에 울려 FOG를 예측할 수 있다. | 원인 미확인(라벨 오차, 이어진 오경보 가능) | 삽화의 54%에서는 라벨 시작 직전 window부터 이미 경보가 켜져 있었다. 동결 직전 변화를 잡은 것인지 라벨 경계 오차인지는 이 분석으로 구분할 수 없다. |
| 이 기술로 웨어러블 로봇이 FOG를 막을 수 있다. | 근거 사다리를 건너뜀 | FOG 검출을 cue나 로봇 제어에 쓰려면 실시간 지연·오경보 시험과 개입 효과의 객관적 비교가 먼저 필요하다. PD 대상 외골격 근거는 아직 드물다(Guo 2022, [R] 15장). |

[Day 40](../../week-6/day-40.md)의 원칙 그대로, 동사(진단한다 → 였다), 범위(10명, 실험실), 크기와 불확실성(평균, 범위)을 고칩니다.

   ```text
   ## 3. 전처리와 window 설계

   - 참가자 평균과 참가자 부트스트랩 구간

   ## 5. 한계
   - 실험실 데이터, 환자 수, 라벨 기준과 경계 오차, 일상 환경 일반화, 약물 상태·FOG 유형 미구분 등 4개 이상

   ## 6. 다음 단계: 임상 cueing과 웨어러블 로봇 제어
   - 근거 사다리의 다음 칸(실시간 지연·오경보 시험, cue 효과의 객관적 비교)
   - 로봇 제어로 이을 때의 조건(오경보 = 보조 타이밍 오류, 주기 가정 제어기의 실패, 걸음당 오류율)
   ```

## 🤖 AI와 함께 하기 (주간 실습, 20–30분)

**이번 주의 기술: FOG 결과 문장과 평가 설계를 AI에게 "반대 심문"받고, 지적을 직접 검증하기**

AI는 보고서 문장을 매끄럽게 다듬는 데 능숙하지만, 그 과정에서 "진단한다", "예측한다", "실시간으로" 같은 강한 표현을 슬쩍 넣거나, 여러분이 쓰지 않은 성능 수치나 논문을 지어낼 수 있습니다. 이번 주에는 반대로 AI를 **까다로운 심사자**로 씁니다. 다듬어 달라고 하지 않고, 과장과 누수와 빠진 정보를 찾아 달라고 합니다.

1. **사실을 먼저 적습니다.** 보고서의 결과 절에서 핵심 문장 5개와, 그 문장의 근거가 된 숫자(참가자 수, 지표의 단위, 검증 방식)를 따로 적습니다. 출처를 확인하지 못한 수치는 "[확인 필요]"로 둡니다.
2. **아래 프롬프트로 검토를 요청합니다.** 원자료나 참가자별 원시 신호는 넣지 않습니다.

   ```text
   나는 보행분석 심화 과정의 캡스톤 보고서를 쓰고 있다.
   주제: 공개 데이터(Daphnet, PD 10명 실험실 가속도계 기록)로 FOG(보행동결) window를 분류하는 모델의 참가자 단위(LOSO) 평가.

   해석 원칙:
   - 결과는 진단·치료 성능으로 표현하지 않는다.
   - 참가자 단위로 나눠 평가했고, window를 무작위로 섞지 않았다.
   - 10명 실험실 데이터이므로 일상 환경이나 다른 환자로 일반화하지 않는다.

   아래 결과 문장 5개를 심사자처럼 검토해 달라:
   [문장 1–5를 붙여 넣기. 숫자는 내 노트북 출력 그대로]

   다음 순서로 답해 달라:
   1. 문장마다 과장되었거나 모호한 단어(예: 진단, 예측, 실시간, 정확도)를 표시
   2. 문장마다 빠진 정보(지표 단위, 분모, 참가자 수, 허용 규칙, 불확실성)를 나열
   3. 평가 설계에서 데이터 누수가 생길 수 있는 지점을 질문 형태로 3개
   4. 고친 문장 제안. 단, 내가 주지 않은 숫자나 논문을 새로 넣지 말 것. 필요하면 "[확인 필요]"로 표시
   ```

3. **AI의 지적을 하나씩 검증합니다.** 누수 질문 3개는 노트북 코드에서 해당 줄을 찾아 "해당 없음(이유)" 또는 "고침"으로 답합니다. AI가 고친 문장에 여러분이 주지 않은 숫자나 문헌이 들어 있으면 지우거나 원문을 직접 확인합니다.
4. **예상 질문 연습:** 같은 대화에서 "이 결과를 듣고 재활의학과 의사와 로봇 공학자가 각각 던질 질문 3개씩"을 요청하고, 그 답을 발표 노트에 씁니다. 답에 필요한 숫자는 반드시 노트북에서 가져옵니다.

**검증 체크**
- [ ] AI가 표시한 과장 단어를 모두 검토했고, 받아들인 수정과 거절한 수정을 이유와 함께 적었다.
- [ ] AI의 수정문에 내가 제공하지 않은 수치·인용이 없음을 확인했다(있었다면 지우거나 원문으로 확인했다).
- [ ] 누수 질문 3개에 코드 줄 근거를 달아 답했다.
- [ ] 발표 예상 질문의 답이 노트북 출력과 일치한다.

> 🔒 **개인정보·데이터 라이선스 주의:** 참가자 원자료(Daphnet 신호 파일, window 단위 예측 파일)는 외부 AI에 올리지 않습니다. 보고서 문장, 요약 표의 숫자, 코드의 구조만 붙여 넣습니다. Daphnet은 CC BY 4.0이라 출처 표시(Bächlin 2010 인용)가 조건이고, zip 안의 논문 preprint PDF는 재배포 대상이 아닙니다. PhysioNet gaitpdb는 ODC-By 1.0입니다. 자격 심사형 데이터는 이용 계약상 온라인 AI 서비스에 넣으면 안 됩니다(자세한 내용은 [심화 E — Day E2](../E-ehr/day-E2.md)). 이 실습은 학습용이며 진단·치료 판단에 쓰지 않습니다.

## 퀴즈

**1.** 보고서에 "민감도 79.6%"라고 쓸 때 반드시 함께 적어야 하는 세 가지는?

<details><summary>정답 보기</summary>

**단위**(0.5초 window), **분모**(FOG가 있는 8명의 참가자별 값의 평균, LOSO), **불확실성**(참가자별 범위 68.1–94.3%, 참가자 부트스트랩 구간). 여기에 데이터의 범위(Daphnet 실험실 기록 10명)를 붙입니다.

</details>

**2.** 부트스트랩 구간을 window 단위로 다시 뽑아 계산하면 무엇이 잘못됩니까?

<details><summary>정답 보기</summary>

같은 사람의 겹치는 window들이 독립 표본처럼 취급되어 구간이 **가짜로 좁아집니다**. 사람 간 차이가 결과를 좌우하는 문제이므로 참가자를 다시 뽑아야 합니다.

</details>

**3.** "삽화의 54%에서 경보가 라벨보다 먼저 켜졌으므로 이 모델은 FOG를 예측한다"는 결론의 문제는?

<details><summary>정답 보기</summary>

먼저 켜진 이유가 동결 직전의 진짜 변화인지, 라벨 경계 오차(수백 ms)인지, 직전 비FOG 구간의 오경보가 이어진 것인지 구분하지 않았습니다. 예측 성능을 주장하려면 pre-FOG 구간을 정의하고 따로 평가해야 합니다.

</details>

**4.** 보고서의 "다음 단계" 절에 넣기에 가장 알맞은 것은?
(a) 이 모델을 바로 웨어러블 로봇에 탑재한다 (b) 실시간 장치에서 지연·오경보를 재고, cue를 켠 조건과 끈 조건을 객관적 지표로 비교하는 시험을 설계한다 (c) 정확도를 99%로 올리기 위해 더 큰 딥러닝 모델을 쓴다

<details><summary>정답 보기</summary>

**(b)**. 근거 사다리의 다음 칸입니다. (a)는 단계를 건너뛰고, (c)는 일반화·오경보·지연 문제를 풀지 않은 채 숫자만 좇습니다.

</details>

**5.** 5분 발표에서 한계에 결과와 비슷한 시간을 주는 이유를 한 문장으로 쓰세요.

<details><summary>정답 보기</summary>

이 결과의 가치는 숫자 자체보다 "어디까지 믿을 수 있는가"에 달려 있고(실험실, 10명, 라벨 오차), 청중이 그 범위를 알아야 결과를 잘못 옮기지 않기 때문입니다.

</details>
